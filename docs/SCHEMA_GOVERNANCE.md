# Schema governance

> How the database is allowed to change. The tables themselves are in `docs/spec/07-Backend-Schema.md`; this file is the rulebook every migration is reviewed against (`/review` Layer 2). `bun run gates` enforces the parts a script can check.

## Migrations

1. Every change is a new numbered SQL file in `apps/api/drizzle/` (`0003_…sql`, `0004_…sql`). One concern per file.
2. **An applied migration is never edited.** `apps/api/drizzle/migrations.lock` holds the SHA-256 of every migration; `bun run gates` fails if one changes. Add a new file's hash in the same commit with `bun run gates --update-lock`.
3. Migrations stay compatible with the previous release (expand, migrate, contract), so a release can be rolled back in under 10 minutes (TR-DEV-08).
4. Every migration is applied in CI to a fresh PostgreSQL 16 and the previous release's tests are run against it (TR-PLT-04).
5. Migrations and schema changes need a senior reviewer (CODEOWNERS).

## Conventions every table follows

| Topic | Rule |
|---|---|
| Names | `snake_case`, plural tables, singular columns; foreign keys `<table_singular>_id` |
| Keys | `id uuid` (UUIDv7 for new tables); human-readable codes (`W-000731`, `INV-2026-00412`) in a separate unique column, generated by a database sequence or a locked counter, never `MAX()+1` |
| Entity | Every business table has `entity_id text NOT NULL`, part of every unique key and every RLS policy |
| Audit columns | `created_at`, `updated_at` (`timestamptz`), `created_by`, `updated_by`; every change also writes `audit_events` |
| Money | `NUMERIC(14,3)` (OMR to the baisa). Other currencies `NUMERIC(16,4)` with a currency column and stored rate. Never `real`, `double precision` or `float` |
| Dates | Calendar dates as `DATE` (Oman time); moments as `timestamptz` (UTC). Never `timestamp without time zone` |
| Names of dates | `<verb>_on` for dates, `<verb>_at` for moments |
| Booleans | `is_` / `has_` |
| Quantities | `_qty`; money `_amount` |
| Effective dating | `valid_from DATE NOT NULL`, `valid_to DATE NULL`; an exclusion constraint stops versions overlapping |
| Status | `text` with a `CHECK` list; changed only through the service method that owns the transition |
| Deleting | Never. `archived_at` and `archive_reason`; foreign keys `ON DELETE RESTRICT` |
| Locking | Final records carry `locked_at`, `locked_by`; a trigger rejects any change after locking |
| Personal data | ID and bank numbers encrypted per column and listed in the anonymiser configuration |
| Legal values | Only in `rule_versions` (dated, signed); never a literal in a migration or in code |

## Security inside the database

- Row-level security on every business table, keyed on `app.entity_id`, `app.user_id`, `app.role`, `app.site_ids`, `app.client_id`, set per request by the API. The API connects as `app_user`, which owns no tables.
- `audit_events` is append-only by trigger and SHA-256 hash-chained; never truncated.
- Locked timesheets, released payroll runs, issued invoices and closed periods are immutable by trigger; corrections are new records.

## Checked automatically by `bun run gates`

- Applied migrations unchanged (lock file)
- No `real`, `double precision` or `float` column type in migrations
- No `timestamp without time zone` in migrations
- No `MAX(...) + 1` in migrations or API code
- Also: only `bun.lock`; golden cases signed or `expected: null`; no Oman IBANs; no hard-coded colours in UI code
